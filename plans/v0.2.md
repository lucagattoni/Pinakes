## Goal

A PDF dropped into `docs/` is indexed, chunked, retrievable and citable by page — and the quality of
the text that made it in is **measured, not assumed**. DESIGN §9 calls PDF extraction *"the most
likely source of silent quality loss"*; the release exists to make that loss visible before it
reaches a user's answers.

v0.2 ships **two** extractors: a free, local, offline default (`pypdfium2`) and an **opt-in paid
Claude-vision extractor** that puts scanned PDFs in scope for the first time. Because a paid path
exists, v0.2 also ships **the whole budget machinery**: §5 says the budget system ships in the same
release as the first thing that can spend, "which is the honest ordering", and that first thing is
now the extractor rather than `pnk ask --deep`. Not scope creep — the design's own rule applied to
the user's decision. Every increment ends **green** (`./check.sh`, equivalently `make check`) and
**committed on its own**, so any regression bisects to one increment.

**Checked dead end — do not re-litigate.** Claude's **citations API** was investigated as a source
of exact character offsets and ruled out. Verified in the Anthropic API reference: a PDF `document`
block returns **`page_location`** (`start_page_number` / `end_page_number`, 1-indexed) —
**`char_location` is returned only for plain-text documents**. Citations are also a paid, query-time
call and are **incompatible with `output_config.format`** (400), the mechanism I7b uses to validate
extraction. So they cannot supply the offsets, cannot be free, and cannot coexist with the
extractor. Decision 4 stands.

**Checked and declined — server-side refusal fallbacks.** The Anthropic guidance is to ship
`claude-opus-5` code with the `fallbacks` parameter on by default (`fallbacks: "default"` under the
`server-side-fallback-2026-07-01` beta), because Opus 5's safety classifiers can decline a request
and a fallback silently rescues it. **v0.2 declines it, deliberately**: a rescued request is served
by a *different model*, and the extraction fingerprint (I7b) hashes the model id. A fallback would
therefore write text produced by one model into a cache entry claiming another — precisely the
silent-provenance failure the fingerprint exists to prevent, and undetectable afterwards. A refusal
here is a page failure with a recorded reason, on a synthetic corpus, which is a survivable outcome;
mislabelled cached text is not. Revisit only if the fingerprint learns to record the model that
actually answered, per page.

## Ground rules (apply to every increment)

- **The gate is an artifact, not a list of commands** (rule 1): `./check.sh` / `make check` passes
  immediately before `git commit`, and every new gate is **added to that script**, never described
  in prose. Two v0.1 commits landed red because the gate was a shell pipeline. New gates and owners:
  extras-not-core (I1), corpus-regenerates (I2), `pdf-eval` baseline (I3b), price-table
  well-formedness (I6a), paid-path allowlist (I7a).
- **A gate that cannot run must say so and still be a gate.** `pdf-eval` and the corpus's scanned
  stratum need `pinakes[pdf]`; gate 4 of the allowlist needs `pinakes[claude]`. Each **skips with a
  printed reason** when its half of the environment is absent (`pdf-eval: skipped — pinakes[pdf] not
  installed`), never silently, and a test asserts the printed reason — a skip nobody can see is the
  vacuous-metric failure (rule 3) wearing a different hat. CI runs the legs that make each gate
  meaningful.
- **Worktree + branch per increment**, `YYYYMMDD_HHMM-i<N>-<slug>` per CLAUDE.md.
- **No inline type suppressions at all** (rule 7). Both that existed in v0.1 hid real defects; the
  Anthropic SDK's response unions are the temptation here, so narrow with an explicit `block.type ==
  "text"` check, never a cast.
- **Test-machinery rules, beside the algorithm rules** (rule 5): a fake must not derive its answer
  from the input under test, so **the fixture generator is not the extractor** and each fixture's
  ground truth is authored from its *spec*; a stand-in must be adversarial in the dimension it
  stands in for, so the registered `fake` extractor — **created by I1 with the registry, and named
  in its tests**, since manifest validation checks registry membership and its presence is therefore
  user-visible — returns deliberately ugly text (double spaces, a stray running head, a hyphen join)
  and the **recorded** paid-API fixtures include a refusal, a schema-invalid page, a truncated
  (`stop_reason == "max_tokens"`) page and a page that drops content; no `or` in an equality
  assertion; a skip condition must check **every half** of its environment claim.
- **Two markers, stated scope.** `pdf` marks tests needing `pinakes[pdf]`, and its predicate checks
  the extra imports **and** the fixture exists. `paid` marks **only** tests that make a real API
  call, and its predicate checks `anthropic` imports **and** a key is present **and**
  `PINAKES_ALLOW_SPEND=1` is set. The recorded-fixture suite is **unmarked**: it must run with
  `anthropic` absent, which is what proves the registry seam. `PINAKES_ALLOW_SPEND` is a **pytest
  condition only, never a product guard** — the product's opt-in is already explicit (`[extraction]
  backend`, `--extract=`, the accountant), and a second env-var gate would be a footgun a user sets
  once in a shell profile and forgets.
- **Test-environment configuration lands in I1** (rule 6): both markers and their multi-part
  predicates, `SOURCE_DATE_EPOCH` pinning for fixture generation, and a probe that **both**
  `pypdfium2` and `anthropic` import silently under `filterwarnings = ["error"]` — a warning at
  import turns every test in that leg red, and the `anthropic` leg is new in this release.
- **Retrospectives are an input, not only an output** (rule 10): re-read `docs/RETROSPECTIVES.md` at
  the *start* of each increment, and land findings and fixes as their **own commit** — v0.1 lost
  that in 5 of 15 increments, and bisectability depends on it. - Docs rule (CLAUDE.md): a
  user-facing surface added in an increment updates its doc home (`docs/README.md`'s routing table)
  and `--help` **in the same commit**; every date carries `HH:MM`; the CHANGELOG `[Unreleased]` line
  lands with the code. **Superseded 20260728: this draft assumed one release, `[0.2.0]`, cut at I9
  — the versioning rule (global CLAUDE.md) instead cut it early, after I5, because I1–I5 already
  passed the SemVer table as complete, self-contained work; `[0.2.1]` followed for the docs
  restructure. Check `main` before assigning the next number (project CLAUDE.md) — do not assume
  I9 still owns a version cut.**
- **CI never spends money.** No CI job holds an API key; the paid path is exercised end to end from
  committed recorded responses. Real-API runs are human-gated (rule 9), with date, model and cost
  recorded.
- **v0.2 must not move the demo KB's eval numbers.** If `make eval` shifts, that is a defect to
  explain, not a tuning opportunity (CLAUDE.md's retrieval rule).

## Prior art: PDFScout

[PDFScout](https://github.com/lucagattoni/PDFScout) (the user's own project, MIT) is a LangGraph
multi-agent PDF extractor on Claude's native PDF vision. I7b is written against it deliberately, and
says so in its module docstring.

**Borrowed.** (a) **The completeness audit against the PDF's own embedded text layer** — PDFScout's
`coverage_node` compares significant words (alphabetic, ≥5 chars, NFKC-folded, order-free) from the
native layer against the model's per-page output and re-extracts pages that dropped or duplicated
content. Here it is *free*, because pypdfium2 already produced that layer in I3b, so it is the paid
path's quality gate at zero marginal cost. It brings PDFScout's own caveat too, which becomes a risk
row: a scanned page has **no usable native layer**, so the audit is blind on exactly the pages the
paid path exists for, and the corpus's hand-authored ground truth is what covers those. (b)
**Per-page schema validation with bounded retries** (≤3), so a malformed page is re-asked rather
than silently truncating the document. (c) **Local pre-checks before any API cost** — page count and
encryption detection, offline.

**Rejected after pass 2 — provider-side prompt caching as the cost strategy.** PDFScout re-sends the
whole document on every per-page request and reports pages 2–N at ~10% of input cost. That figure is
real but it is a *hit-path* figure over a cost the design creates: re-sending an N-page document N
times is `N × doc_tokens` of input where sending each page once is `N × page_tokens`. The quadratic
term is what caching then discounts. Two consequences make it unusable rather than merely expensive:
`doc_tokens` exceeds `claude-opus-5`'s **1M context window** at roughly **166 pages** at this plan's
own 6,000-tokens-per-page constant — below the 600-page API limit the pre-check tests, and below the
200-page case this plan works through — and the `ephemeral` marker is a **5-minute** TTL, so any run
longer than five minutes re-pays the 1.25× write repeatedly. v0.2 sends a **K-page slice** instead
(decision 8): each page is sent exactly once, input is linear, there is no page ceiling, and no cost
claim depends on a cache that expires mid-run. Caching may return in v0.3 as an optimisation *on top
of* a linear baseline, where a cache miss costs a discount rather than an order of magnitude.

**Rejected.** *LangGraph and the multi-agent graph* — pinakes has one extraction task, and a graph
framework is exactly the "second, worse agent framework" §9 names as a risk. *The classifier and
hierarchy agents* — they produce a document tree; pinakes needs linear text with page spans, and a
hierarchy would be a second structure with no consumer (v0.1's I6 is the record of what an unused
structured column costs). *SQLite checkpoint/resume* — resume uses per-page staging files inside the
extraction cache instead (I7c), rather than a second durability surface beside the cache and
per-document transactions that already exist. *Per-page parallel fan-out, in v0.2* — the hard cap is
a **running** reservation total (§5) and concurrent calls can breach it between reservation and
reconciliation; parallelism lands in v0.3 once the accountant has a ledger to prove itself against.

## What this plan deliberately does NOT decide

- **Table structure recovery.** The table stratum measures whether a table's text survives in
  readable order with label/value adjacency intact — not whether a grid is reconstructed as a grid.
- **PDF outlines/bookmarks as a `heading_path` substitute.** Pages are the unit v0.2 ships.
- **The Files API** (`files-api-2025-04-14`) instead of base64 document blocks. It uploads once and
  references a `file_id` across requests, but needs the beta header on **both** the upload and the
  message call plus an upload lifecycle to clean up. Under decision 8 each request carries a
  *different* K-page slice, so there is nothing an upload would be reused across within a document.
  **Default: base64 slices.** Revisit only if slices become large enough that upload bandwidth, not
  tokens, is the cost.
- **Figures, embedded images, captioning** beyond what the paid extractor's page output already
  says; Office, HTML, email, chat (§1 rules them out); any change to chunking parameters, fusion,
  reranking or the confidence signal; `pnk link` and cross-KB traversal (v0.3); `sqlite-vec` (v0.5).
- **`pnk ask --deep`** — still v0.4; v0.2 ships the budget machinery it will use, not the loop.
  **Default:** the accountant's "operation" for v0.2 is one `pnk sync` invocation — which bounds a
  single invocation and nothing else, so the day and month windows (I6a) are what bound a *sequence*
  of them.

### I2 — The synthetic hard-case PDF corpus and its generator

`tests/pdf-corpus/`: a committed generator, the committed PDFs it produces, and one hand-authored
`<name>.expected.txt` per fixture. **No real-world PDF is ever committed** (CLAUDE.md: the repo is
the engine). Ground truth comes from the generator's *spec*, never from extractor output — otherwise
the test asserts only that the extractor agrees with itself. Sized **per stratum, not in aggregate**
(rule 4 — v0.1 sized its golden set at ≥40 in aggregate and still ended with an 8-question no-answer
stratum it had to label a floor):
| Stratum | n | Must contain |
|---|---|---|
| Stratum | n | Pages | Must contain |
|---|---|---|---|
| two-column | 3 | 6 | reading order across a gutter; a caption straddling both columns; a left column ending mid-sentence. **`two-column-a` is a named paid twin** |
| tables | 3 | 6 | a bordered grid; a borderless whitespace-aligned table; one with a spanning header cell. **`tables-bordered` is a named paid twin** |
| headers / footers | 3 | 16 | a repeating running head; page numbers; a footer present only on page 1. **`headers-repeating` is a named paid twin** |
| ligatures & hyphenation | 3 | 6 | U+FB01/U+FB02; a soft hyphen; a word split across a line break **and** one across a page break. **`ligatures-a` is a named paid twin** |
| **scanned / image-only** | 3 | 10 | one 6-page and two 2-page fixtures, rastered from known glyph coordinates with **no text layer** — clean (6pp), skewed 2° (2pp), low-contrast (2pp). The 6-page fixture is deliberately **larger than K = 5**, so a paid run crosses a slice boundary and exercises the short final slice; the draft's "2 pages each … exercised at a slice boundary" is impossible, since `ceil(2/5) = 1`. This is the stratum the paid path exists for |
| pathological | 2 | 2 | a text layer in invisible render mode; a truncated/corrupt-header file |
| baseline | 2 | 13 | plain single-column prose, one page and twelve pages. **`baseline-12p` is a named paid twin** |

Nineteen documents, **59 pages** — a stated total, derived from the column above rather than
asserted loosely, and checked by `::test_stratum_page_counts` so "≥45" cannot quietly become 20. The
headers/footers stratum carries 16 rather than 9 because its repeating-head fixture is 10 pages, the
resolution *T*'s fit needs (I3a).

**≤ 2 MB committed in total, of which the scanned stratum's ten pages are ≤ 1.5 MB.** The headroom
is thin and the arithmetic says so rather than the first regeneration run: six clean pages at ~120
KB leave `(1500 − 720)/4 = 195 KB` for each of the four skewed and low-contrast pages — only
**1.63×** a clean page, on exactly the pages that compress worst, since a 2° rotation destroys the
axis-aligned runs Flate exploits. If generation exceeds it, the fix is a lower DPI or fewer scanned
pages, decided here rather than under a red gate. The text-layer half is comfortable: `2 − 1.5 = 0.5
MB` over 49 pages ≈ 10 KB/page against 1–3 KB actual for raw base-14-font content streams.

**Five fixtures are named `paid twins`** — one per stratum where `layout.py` does real work, plus
the 12-page baseline as a control. They are the documents I7b's human-gated run re-extracts through
the paid backend to measure decision 10's free-vs-paid delta. Naming them here is what makes that
measurement runnable: it needs healthy text-layer PDFs (so `--force` on each), it must cover the
dimensions where bypassing `layout.py` can matter rather than only prose, and a set nobody named is
a measurement nobody can repeat.

The generator writes raw content streams for the sixteen text-layer fixtures, no layout engine and
**no dependencies**: those fixtures are not documents, they are **text layers with known
coordinates** using the PDF base-14 fonts, and a layout engine would hide the variable under test
behind its own decisions.

**The scanned stratum is generated differently, and gated differently.** It rasters the *same*
coordinates as its text-layer twin, so its ground truth is identical to the twin's — which makes
free-vs-paid directly comparable on the same content. Producing that raster needs a renderer and an
image writer: `pypdfium2` (the `pdf` extra, already present) renders the twin's page to a bitmap,
and **Pillow** (new, in the dev dependency group only — never core, never an extra) applies the skew
and contrast transforms and writes the image-only PDF at 150 dpi, 8-bit grayscale, Flate-compressed.
JPEG is never used: JPEG encoders differ across builds, and lossless Flate keeps the pixels the
generator produced. Rendering is not extraction, so rule 5's "the generator is not the extractor"
holds — the ground truth still comes from the spec.

**Byte-identical regeneration is not achievable for rasters** and pretending otherwise would make
the gate CI-flaky on any pdfium or Pillow bump. So the gate splits: the sixteen text-layer fixtures
must regenerate **byte-identically**; the three scanned fixtures are checked by structure (no text
layer, expected page count, image geometry and colour mode) plus a pixel-difference tolerance.

**The tolerance is a changed-pixel fraction, not a whole-page mean, and the arithmetic is why.** A
mean absolute difference of ≤ 2/255 sounds strict and is not: at 150 dpi an A4 page is 1240 × 1754 =
**2,174,960 px**, so a moved 10 pt word at ~20% ink changes ~682 px and moves the mean by ≈0.08.
Reaching 2.0 would take ~17,059 fully flipped pixels — **about two moved lines of text**, counting
both the vacated and the occupied ink at 20% coverage. A whole-page mean therefore accepts arbitrary
reflow while claiming that "a moved word must" fail it. So the gate is: **more than 300 pixels
differing by more than 32 levels is a failure** — an absolute count, ~0.014% of the page. The count
has to be derived, because the obvious fraction is wrong twice over: 0.1% of 2,174,960 px is 2,175
px, while a moved 10 pt word changes ~682 px on the plan's own realistic-ink model (mean 0.08 →
`0.08 × 2,174,960 / 255`) — so a 0.1% gate **passes** a moved word exactly as the whole-page mean
did. One ink model, stated once: a 6-character 10 pt word at 150 dpi occupies a ~62 × 15 px box at
~20% ink ≈ 200 ink px, and moving it changes both the vacated and the occupied ink ≈ **400–680 px**.
300 sits ~2× under that signal and ~7× over sub-pixel noise on a handful of glyphs. The computation
and this arithmetic go in the test's docstring, so the next reader checks the number rather than
trusting it. A renderer bump that exceeds the tolerance is handled by regenerating and committing
the new rasters in a commit that says so.

**Regeneration is deterministic outside pytest too.** `SOURCE_DATE_EPOCH` is pinned in pytest
configuration (rule 6), but `make corpus` and `check.sh` run the generator *outside* pytest — so the
generator sets it itself when unset, and the `check.sh` gate exports it explicitly. Without that,
the gate's own regeneration rewrites the committed fixtures with fresh `CreationDate`s and then
reports the diff it just created.

**Tests:** `tests/test_pdf_corpus.py` — byte-identical regeneration of the text-layer strata (fixed
producer string, `CreationDate`/`ModDate` from `SOURCE_DATE_EPOCH`); the scanned stratum's
structural + tolerance check, `pdf`-marked and skipping with a printed reason when the extra **or
Pillow** is absent — the marker's predicate checks all three parts of its environment claim, not two
(rule 5, in the increment that first needs the third); every fixture has a ground truth and every
ground truth a fixture; stratum counts **and page counts** match the table, so the corpus cannot
silently shrink; the committed byte budget holds; `::test_named_paid_twins_exist`, so I7b's
human-gated measurement cannot reference a fixture nobody committed. **Exit criteria
(repo-verifiable):** `make corpus` leaves no diff on the text-layer strata and no tolerance breach
on the scanned stratum, and that check is a gate in `check.sh` that skips the scanned half with a
printed reason when its dependencies are absent. **Not** an exit criterion: any claim about
extraction quality — nothing extracts yet.

### I3a — Extraction core, pure (rule 11: the pure half)

`extract/layout.py`, operating only on the I1 types — no PDF library, no filesystem:

- `blocks_from_chars(chars) -> list[Block]` — pdfium's text API is **character-level**, and turning
  a character stream into blocks is the single densest piece of logic in the extraction path. It
  lives here, pure and table-driven against hand-built character streams, rather than inside the I/O
  adapter where it would be reachable only through an end-to-end corpus score (rule 11). -
  `reading_order(page)` — column detection by x-gap clustering, then top-to-bottom within a column.
- `strip_running_heads(pages)` — a line recurring in the same y-band on ≥ *T* of pages, digits
  normalised, is a running head. ***T* = 0.6, and it is fitted, not guessed** — it changes the
  extracted text and therefore the free backend's fingerprint, so a bare constant would be exactly
  the "threshold with no provenance" I3b refuses elsewhere. I3b fits it over the headers/footers
  stratum (whose spec states which lines are running heads and which are genuine headings) and
  commits it with `fitted_on` beside the text-yield floor; 0.6 is where the fit begins, not the
  shipped answer. **The fit needs resolution the draft's stratum could not give it**: at 3 pages per
  document a per-document recurrence can only be 1/3, 2/3 or 3/3, so *every* T in (1/3, 2/3]
  reproduces the corpus identically and "fitted" would name a value the data never chose. The
  repeating-running-head fixture is therefore **10 pages**, giving resolution 1/10. **T reaches
  `layout.py` as a parameter, never a file read** — this module is pure and `test_layout_is_pure`
  asserts it — so the caller passes it in and I3a's table-driven tests are parameterised on it
  rather than hard-coding 0.6. **The threshold ships with its denominator**: the result reports
  `suppressed N of M pages`, so a wrong *T* is visible instead of silently eating a real heading.
- `join_hyphenation(lines)` — join a trailing hyphen or U+00AD when the continuation starts
  lowercase; never join across a heading or a suppressed running head.
- `normalise(text)` — ligature expansion (U+FB00–U+FB06), NFC, an explicit whitespace policy. **It
  lives in `extract/textpolicy.py`, not here** (decision 15): it is the one stage *both* backends
  run, it is pure string→string with no geometry, and leaving it inside `layout.py` made decision
  10's claim that the paid backend "bypasses `layout.py`" false — while `LAYOUT_VERSION`'s exclusion
  from the paid fingerprint then left a whitespace or ligature change invisible to every paid cache
  entry and to §4.4. It carries **`TEXT_POLICY_VERSION`**, hashed into **both** backends' inputs.
  **It is length-changing** — one ligature codepoint becomes two or three, NFC composes, whitespace
  collapses — so the increment that emits offsets states the order explicitly (below), and the paid
  backend states it too (I7b).
- `assemble(pages) -> ExtractedText(text, page_spans, per_page_provenance)` — three fields, the same
  three everywhere (I1); the free backend supplies an empty `per_page_provenance`. **Offsets are
  emitted with the text, never accumulated afterwards** (v0.1 I6: spans from `match.start()` rather
  than a running total are exact by construction rather than by accounting). **Offsets are computed
  *after* `normalise()`, never before** — stated because `normalise()` is length-changing, so
  computing spans on pre-normalised text puts every offset past the first ligature out by one or
  two, while the spans still tile perfectly and no property assertion can see it.
- `LAYOUT_VERSION` — a hand-bumped constant hashed into the fingerprint of **every backend that runs
  this module**, because a change to reading order or hyphenation changes the extracted text as
  surely as a library upgrade does, and would otherwise be a silent cache hit. With `normalise()`
  moved out (decision 15), that is genuinely the free backend only, and the split is now honest in
  both directions: a reading-order refactor cannot invoice a paid KB, and a whitespace-policy change
  cannot slip past a paid fingerprint. A free-path constant must not be able to send an invoice —
  and a shared constant must not be able to hide behind that rule.

**Tests:** `tests/test_extract_layout.py`, table-driven — one case per rule, plus the compound cases
a table cannot express: a two-column page continuing mid-sentence into the right column; a running
head that is a genuine heading on exactly one page; a hyphenated word split across a page break
where the next page opens with a running head. `blocks_from_chars` gets its own dense table:
characters out of reading order, a word split across two text runs, overlapping bounding boxes, a
zero-width character, and a page with no characters at all.

**Three property assertions over every case, and the third is the one that matters.** The draft
named two — `"".join(text[s:e] for s, e in page_spans) == text`, and `page_spans` contiguously
covering `[0, len(text))` — which are **one property and its own corollary**: contiguous
non-overlapping coverage *entails* the join identity, so the pair is the tautological-test shape
this repo already killed once (`docs/RETROSPECTIVES.md`, I2). Worse, neither says *which page* a
span belongs to: `page_spans = [(0, L), (L, L), (L, L), …]` satisfies both, and every `page_start`
in the index silently becomes 1. So the third assertion is **content-anchored**: for each page, a
sentinel string the fixture spec places on that page and no other must fall inside that page's span.
That is the assertion a wrong page number cannot survive. **Exit criteria (repo-verifiable):** one
named test per rule and per compound case; all three properties hold across all of them; an
import-graph test asserts `layout.py` imports no PDF library and `textpolicy.py` imports neither
that nor `layout.py`.

### I3b — The pypdfium2 adapter, the quality metrics, and the two fitted floors (rule 11: I/O)

`extract/pdfium.py` is a **thin reader**: open a file, guard its size against **256 MB** (a stated
number, tested at the boundary — large enough that no legitimate corpus document trips it, small
enough that a runaway file fails fast instead of exhausting memory), refuse an encrypted or
corrupt-header file with a named error, and emit `list[CharSpan]` per page for I3a's
`blocks_from_chars` to assemble. It also exposes **`slice_pages(path, first, last) -> bytes`**,
which writes a K-page sub-document — I7b's request unit (decision 8), put here because this is the
module that owns pdfium and I7b must not become a second PDF I/O boundary. **The API is verified
against pypdfium2 5.12.1 (20260727 17:00), not assumed:** `PdfDocument.new()`, `import_pages(pdf,
pages=None, index=None)` and `save(dest)` all exist, and a round trip over a 12-page document
produced a 5-page slice and a 2-page short final slice, ~1 KB each. Decision 8 rests on this call
existing in the BSD-licensed library the project already chose, so it is checked here rather than
discovered at I7b. Everything that decides *what the text is* lives in the pure half; what remains
here is I/O, and that is where review effort is budgeted (rule 11's corollary: v0.1's pure half
produced one finding and the I/O half four, all environmental).

Its option set is **pinned and hashed** into the fingerprint. Fingerprint **inputs** are declared in
I1's client-free registry entry and hashed by one shared pure function — per-backend *inputs*, not
one shared formula, because a shared formula would hash `pypdfium2`'s version for a backend that
never loads it while omitting the model that actually produced the text (pass 1, H4); and inputs
rather than a method on the backend, because §4.4's per-document check runs on every query and must
never import a paid client to ask a question about a fingerprint (pass 2, M-1). This backend's
inputs are backend name, pypdfium2 version, pdfium build, the option dict, `LAYOUT_VERSION` and the
fitted running-head threshold *T*; the paid backend's are stated in I7b. The value is written to
`documents.extraction_fingerprint` (with `documents.extraction_backend`) at sync, and into the I4
cache key.

`extract/quality.py` scores an extraction against a ground truth. **Every rate ships with its
denominator as a co-metric** (rule 3 — v0.1's `false_abstain: 0.0` was vacuous and would have passed
a CI gate forever):
| Metric | Numerator | Denominator |
|---|---|---|
| `char_recall` | expected non-space characters found, in order | expected non-space characters |
| `order_fidelity` | LCS length over word sequences | expected word count |
| `junk_rate` | extracted words absent from the ground truth | extracted word count |
| `pair_adjacency` | asserted (label, value) pairs within **80** characters of each other — a bare constant with a stated basis rather than a fit: correct reading order puts a label and its value 0–40 characters apart, a reading-order failure puts them hundreds apart, so any value in ~50–150 separates the two cases and 80 is the midpoint | asserted pairs |
| `word_coverage` | significant native-layer words present in the extraction | significant native-layer words |
| coverage | `documents_scored`, `pages_scored` | `documents_total`, `pages_total` |

`word_coverage` is the PDFScout completeness audit, defined here as a pure function of two strings
so it can be tested against hand-computed answers; I7c consumes it as the paid path's re-extraction
trigger, and a metric that can be wrong on a known input is not fit to gate anything.

**v0.2 fits exactly one threshold that gates spending, and says plainly why the other cannot be
fitted yet.**

- **There is no `word_coverage` floor in v0.2** (decision 12). Two review passes each tried to fit
  one and each picked a pair that is not the pair it is applied to: against the hand-authored ground
  truth (the draft), then against pypdfium2's own extraction (pass 2's fix). The applied pair is
  (native layer → **Claude's** output), and **no Claude output exists at I3b**, so the correct pair
  is unavailable by construction. Fitting against pypdfium2 is worse than arbitrary: pypdfium2's
  extraction *is* the native layer transformed by `layout.py`, so that distribution measures
  `strip_running_heads` and `join_hyphenation` rather than extraction fidelity — and the six
  non-scanned strata include the corrupt-header fixture this increment's own reader contract
  requires to **raise**, so a 5th percentile over ~16 values is the minimum in all but name and the
  floor lands near zero, leaving the audit inert on every installed copy. The metric ships, is
  scored and is reported; the threshold and the re-extraction loop land in **v0.3**, fitted on a
  real distribution. A threshold that spends money may not be guessed, and "fitted" against the
  wrong population is a guess wearing a measurement's clothes.
- **The `text yield` floor is fitted here**, because its pair *is* available: it compares a free
  extraction against nothing at all — it counts characters. Non-whitespace characters **per page**;
  the three scanned fixtures are the positive control at zero, the twelve-page baseline the negative
  control. It is consumed by I7b's free-path pre-check *and* I8's `pnk doctor` check, so it is
  defined here rather than in either, because neither may define it for the other. **Its blind spot
  is stated rather than discovered:** the pathological stratum's invisible-render-mode fixture
  yields characters while being useless text, so it clears the floor and still needs the paid path.
  The fitting population contains no bad-but-nonzero case, so this floor separates *empty* from
  *non-empty* and nothing finer. `--force` is the documented escape and `pnk doctor`'s remedy says
  so.

**The floor ships as package data and fails closed when absent.** `extract/floors.toml` sits beside
I6a's `prices.toml` in the wheel, written by the fitting run and carrying each value's `fitted_on`
(corpus revision + `YYYYMMDD HH:MM`). `tests/pdf-corpus/baseline.json` is a *test* artifact and is
not installed, so keeping the floor only there would give every installed copy of pinakes no floor
at all while two runtime consumers on a user's own KB depend on it. **Absent the fitted floor, the
paid path refuses to run** rather than paying to re-extract a PDF it cannot prove is unhealthy — the
same fail-closed shape as v0.1's `confidence: unknown`. `floors.toml` is packaged and asserted here;
**`prices.toml` is I6a's to package and assert**, with its own
`::test_prices_are_installed_package_data`, because a file that ships from a source tree and not
from a wheel is broken on every installed copy from I6a to I9 with the whole suite green — the exact
failure this paragraph identifies for floors. I9's wheel smoke asserts both in the built artifact,
so neither rests on a source-tree test alone. The running-head threshold *T* (I3a) is fitted in the
same run and written to the same file; it costs no money, so its absence is a startup error rather
than a refusal to spend.

**Nothing here re-fits automatically, so `fitted_on` can go stale while still reading as evidence.**
A `layout.py` or `textpolicy.py` change silently invalidates *T* and any committed floor. `make
pdf-eval` therefore recomputes the floors and **fails if a committed value has drifted** beyond the
per-stratum tolerance — the fit is a gate, not a one-time ceremony.

### I4 — The extraction cache

`extract/cache.py`. One JSON per entry — `{schema, content_hash, backend, fingerprint, page_count,
page_spans, text, per_page_provenance, operation_id, call_ids}` — because a text/JSON pair
introduces a half-written-pair corruption class that need not exist. It stores exactly I1's
`ExtractedText` plus its provenance, so what a cache **hit** returns is what a cache **miss**
returns; a draft in which I5 consumed "the extraction's blocks" while the cache stored only text and
spans would have worked on every miss and failed on every hit, which is rule 2's failure shape in
the one increment pair the plan cites to justify the trace test.

`operation_id` and `call_ids` are the join key to the ledger. Without them I7c's promise that
`--clear-cache` prints what the cached entries cost is unimplementable: no cache entry recorded a
call and no ledger line records a document, so there was nothing to join on. `call_ids` is a list
because one paid document is several K-page requests (I7b); both are `null` for a free extraction,
which costs nothing and joins to nothing. The ledger's no-content rule is untouched — the identifier
travels from the cache to the ledger, never document text from the ledger to anywhere.

Written to a sibling temp and `os.replace`d. Invalidation is **by key, never by mutation**: an
edited PDF or a changed fingerprint simply misses.

```text
.pinakes/ ├── index.db          ← disposable, rebuilt ├── ledger.jsonl      ← NEVER touched (§6.3)
└── cache/extract/ ├── <content_hash>-<fingerprint>.json      ← a complete extraction └──
partial/<content_hash>-<fingerprint>/  ← per-page staging, written only by I7c
```

Eviction: after a **fully successful** sync, entries whose `content_hash` matches no active document
are removed — never after a run that recorded failures, never during `--sidecars-only`, never during
`--rebuild` before the swap succeeds, and **never for an entry written by a paid backend**. That
last exclusion is the same rule I7c writes into CLAUDE.md, applied to the path that would otherwise
break it silently: a soft-deleted document (§6.4 keeps `state = deleted`) is not an "active
document", so a routine delete or an un-sidecarred rename would sweep away an extraction the user
paid for — with no prompt and no printed euros, while the *manual* `--clear-cache` gains both. Paid
orphans are **reported** by the sweep and by `pnk doctor` — as `paid orphans: N` here, since neither
the ledger reader nor a paid cache entry exists yet, and **I7c adds the euros** in the same commit
as `--clear-cache`'s. That is the split this increment already makes for `--clear-cache` a few lines
below; making it for one line and not the other is how a forward reference ships. They are removed
only by an explicit `--clear-cache=paid`. `pnk sync --clear-cache` (named in §6.3, never
implemented) empties `cache/` only; `--rebuild` leaves it alone, which is the whole point of a
cache.

**`--clear-cache` confirms before it destroys.** It prints the entry count and bytes it is about to
remove and requires a `y`; `--yes` skips the prompt for cron use. I7c extends the printed summary
with the euros those entries cost, read from the ledger, and amends CLAUDE.md's "`.pinakes/` is
disposable" invariant to except the paid extraction cache — the two halves are split because the
paid entries and the ledger reader do not exist until then, and a plan that pretends otherwise is a
plan with a forward reference in its code.

`pnk doctor` reports entry count, bytes, `orphans / entries`, and paid orphans separately.
**Tests:** `tests/test_extract_cache.py` — a second sync of an unchanged PDF calls the adapter
**zero** times (spy-counted); a changed document, a changed fingerprint and a truncated cache file
each miss rather than crash; two KBs holding the same PDF get two cache files;
`::test_the_sweep_spares_paid_entries` — a soft-deleted document whose entry was written by a paid
backend survives a fully successful sync and is reported, while its free twin is swept. Plus
`tests/test_sync.py::test_clear_cache_preserves_the_ledger` and
`::test_clear_cache_without_yes_and_without_a_tty_aborts`. **Exit criteria (repo-verifiable):** the
zero-call assertion; the ledger-survives assertion; the paid-entry survives the sweep;
`--clear-cache` and `--yes` in `pnk sync --help` and in §6.3's prose in the same commit.

### I5 — PDF chunking, page provenance, and the span invariant (`schema_version` 2)

`chunk_document(kind="pdf")` consumes **I1's `ExtractedText`** — text plus `page_spans`, the same
object on a cache hit and a cache miss — and splits at page boundaries so a chunk never spans two
pages without recording both. It does not consume blocks: blocks are the free backend's internal
geometry, the cache never stored them, and the paid backend never had them. The `_fit` / `_atomise`
machinery is reused unchanged — and its guarantees are **re-asserted for the new path, not
assumed**: the token limit, never-trim, and the overlap-must-not-breach-`max_tokens` rule that
v0.1's I6 found broken. `store.py`: `chunks.page_start` / `page_end` (INTEGER, NULL for non-paged
sources), `ChunkRow` and `Chunk.as_row()` grown together (already coupled), `SCHEMA_VERSION = 2`.
`heading_path` stays **NULL** for PDFs — a PDF has pages, not headings, and stuffing `"p. 7"` into a
free-text filter/citation column is v0.1's I6 defect rewritten.

**The fingerprint is per document, not per index.** `documents` gains `extraction_backend` and
`extraction_fingerprint` (TEXT, NULL for non-extracted sources). A single `meta` key could not
describe a corpus where `pnk sync --extract=claude-vision` ran over some documents and the free path
over others — which the CLI explicitly allows — so it would either be wrong or refuse every query on
a perfectly coherent KB after any `--extract` run. §4.4's coherence gate therefore checks **each
document against its own recorded backend**: for every distinct `(backend, fingerprint)` pair among
active documents, re-derive that backend's current fingerprint **from I1's client-free registry
inputs** and compare. Any mismatch **refuses the whole query**, naming the affected documents and
the count, with the same remedy shape as a model mismatch — partial results from a half-stale index
are the silent-garbage failure §4.4 exists to prevent.

**A free mismatch refuses; a paid mismatch WARNs and marks** (decision 13). The draft refused both,
which meant a `uv lock --upgrade` bricked every paid KB: `claude-vision`'s inputs include
pypdfium2's version and pdfium's build (I7b), the fingerprint is in the cache key, and the remedy —
a rebuild — is therefore a cache miss and a fresh invoice. The model-mismatch precedent the draft
borrowed does not transfer: embeddings computed under a different model are *meaningless*, so
refusing is the only honest answer, whereas text extracted by an earlier extractor version is still
**correct text** — merely older. So a paid mismatch WARNs in `pnk doctor`, and every affected result
on both surfaces carries a `stale_extraction` marker naming the recorded fingerprint. The free
backend keeps the hard refusal, because there the remedy costs nothing.

Resolving inputs rather than importing the backend is what makes this affordable and safe. The draft
had the check re-derive the fingerprint from a method on the backend, which on a KB holding one paid
document would have imported `anthropic` **on every query** — violating the invariant I7a's gate 4
asserts, and passing CI only because that gate's run list uses a KB with no paid documents. It also
carried a false rationale for skipping: an absent `anthropic` was said to mean the extraction cannot
have changed, but claude-vision's fingerprint inputs are model id, prompt version, schema version
and request-shape version — **all package constants**. A `pinakes` upgrade that bumps the prompt
genuinely changes the extraction whether or not the SDK happens to be installed, so the skip
disabled the check on precisely the backend where staleness costs money. With inputs in the registry
the check **always runs**; the only genuine skip left is a backend name the registry does not know
at all (a KB written by a future version), which `pnk doctor` WARNs about and queries proceed past,
because a fingerprint that cannot be computed cannot be compared.

**The backend is part of the change decision, in the paid direction only** (decision 9). The
decision table lives in **`pairing.py`**, not `sync.py` (`sync.py:3`: *"The decisions all live in
`pairing.py` (§6.4); this module does the I/O around them"*), so the work lands there:
`pairing.IndexedDocument` gains the backend, `read_index_snapshot`'s `SELECT` (`sync.py:180`) gains
the column, and `pair()`'s ordered table gains the clauses below. Naming the wrong module is how an
increment's review effort lands on the wrong file. §6.4's "path and hash unchanged → skip" was the
only re-processing trigger, so two silent failures followed from I6b's hook rule and I4's cache
respectively: a scanned PDF committed while hooks force `--extract=pypdfium2` is indexed as empty
and then **skipped forever** by every later manual sync, on a KB whose manifest asks for the paid
backend; and `--rebuild` re-extracts a paid document with whatever the manifest says, missing the
paid cache entry and overwriting it with pypdfium2's empty output. §4.4 cannot see either, because
each document still matches *its own recorded backend* — which is now the free one. Both are the
silent quality loss §9 names as this release's reason to exist. The rule:

- A document whose recorded backend is **free** and whose effective backend for this run is **paid**
  is stale: it is re-extracted, subject to every cap and confirmation. - A document whose recorded
  backend is **paid** and whose effective backend is **free**, with an **unchanged** content hash,
  is **never** re-extracted. Not by a hook, not by `--rebuild`, not by `--extract=pypdfium2`. The
  existing extraction stands and the run says so once. Only `--force` **together with an explicit
  free `--extract`** overwrites it, and it prints what it discards first. - The same document with a
  **changed** content hash is neither skipped nor overwritten: it is a **`failures` row** naming the
  path, the run exits non-zero, and the remedy names the paid re-extraction (decision 14). This is
  the collision §6.4's ordered table would otherwise resolve silently in favour of "hash changed →
  re-chunk", and it is the *common* case, not an exotic one: hooks force the free backend on every
  commit, so re-scanning a paid-extracted PDF hits it. Letting the hash win overwrites paid text
  with pypdfium2's empty output on an image-only PDF; letting the backend win leaves the index
  describing a file that no longer exists, permanently, because the hash never changes again. A
  failure row is the only outcome where nothing is silently wrong, and it isolates per document
  exactly as v0.1 already does.
- `pnk doctor` lists all three gaps by path: documents awaiting a paid extraction, documents whose
  paid extraction the manifest no longer asks for, and paid documents whose file has changed.

**`pnk sync` gains `--force` here**, in the increment that first needs it — not at I7c, which only
*completes* its two-part scope. `cli.py:334` has `--force-unlock` today and nothing else, so I5's
`test_backend_drift` case 5 and I7b's healthy-PDF refusal would both have referenced a flag that did
not exist. That is pass 2's hooks-shipping-an-unbuilt-flag defect for the third time, and this is
where it stops.

**Provenance lives in the sidecar, because `--rebuild` discards the index** (decision 11). Verified
against `sync.py:231-241`: a rebuild opens `<index>.db.new`, calls `store.create(target)`, and then
reads `before = read_index_snapshot(connection)` from that **empty** database — so every document is
"new" and nothing above can consult a recorded backend that lives only in `index.db`. I5's own "a
paid-indexed PDF is not re-extracted by `--rebuild`" case is unimplementable without this. So the
sidecar's existing `provenance:` block gains `extraction: {backend, fingerprint, extracted}`, and
`documents.extraction_backend` / `extraction_fingerprint` become the index's *cache* of it, seeded
from the sidecars on a rebuild.

This is deliberately **not** the content hash DESIGN §2.2 refuses to put there, and the amendment
says so in the same breath: a content hash dirties the sidecar on every document edit and is stale
in exactly the window between an edit and the next sync. The extraction record changes only when the
*extractor* changes, is written by the same sync that does the extraction, and is stale in no state
the index can detect — which is why it must survive the index rather than live inside it. It is also
what DESIGN §2's own rule requires: anything that must outlive the index lives in a committed file.
**Writing it is new code, and the cost is real.** Verified: `write_sidecar` has exactly two call
sites — inside `_mint` (`sync.py:392`), which runs only when `doc_id is None`, and inside
`_write_missing_sidecars` (`sync.py:415`), the `--sidecars-only` path. A document that **already has
a sidecar** — precisely decision 9's case — is never rewritten today, so I5 adds an additive
read-merge-write for `provenance.extraction`. Two consequences, both accepted deliberately:

- **`sidecar.py`'s own docstring defers this**: *"In v0.1 sidecars are created and moved, never
  rewritten in place, so PyYAML dropping comments on dump costs nothing yet. `pnk link` (v0.3) is
  what will need a comment-preserving writer."* v0.2 pulls that forward without solving it, so a
  hand-annotated sidecar **loses its comments and has unknown keys re-sorted** the first time that
  document is paid-extracted. The write happens only on a deliberate paid extraction, never on a
  hook; the alternative was building v0.3's round-trip writer here, which is a whole increment of
  unasked-for scope. CLAUDE.md's "`docs/` belongs to the user" gains the sentence that sync now
  writes `provenance.extraction` into an existing sidecar.
- **`--index-only` cannot write into `docs/` at all** (`sync.py:388-390` returns before the write,
  and `test_index_only_never_writes_into_docs` asserts it). That contract is **kept**: a paid
  backend under `--index-only` is **refused** with a remedy naming a normal sync. It costs nothing,
  because `--index-only` is what the `post-commit`/`post-merge` hooks run and I6b already forbids
  hooks from spending.

A document with no sidecar yet has no protection and is treated as free-extracted, which is correct
— a paid extraction is a human invocation, and a human invocation writes the sidecar. **Tests:**

### I6a — Budget core, pure (rule 11: the pure half of the money machinery)

`src/pinakes/budget/`, with **no I/O and no `anthropic` import**. `prices.toml` ships in the wheel
like the templates, carrying `as_of` as `YYYYMMDD HH:MM`, per-model `input_per_mtok_usd` /
`output_per_mtok_usd`, and — because the manifest prices in EUR and the vendor in USD — a
`usd_per_eur` rate carrying the **same** `as_of`. It does **not** carry cache-write or cache-read
multipliers: decision 8 removed the only marker that would have used them, and a shipped constant
with no consumer is the unused-column cost v0.1's I6 already paid. Seeded from the current table:
`claude-opus-5` at $5.00 / $25.00 per MTok, with `usd_per_eur` seeded at **1.08** carrying the same
`as_of`. The rate is stated because every euro figure in this plan depends on it — a slice is
$0.3515 ≈ €0.32 only at 1.08 — and a euro number whose rate is implicit is exactly the unprovenanced
figure I6b's ledger rule exists to prevent. Euro figures below hold at the seeded rate.

**`estimate.py` estimates over *requests*, and a request is a K-page slice** (decision 8). Getting
the unit wrong is the difference between a reservation that bounds a run and one that is wrong by an
order of magnitude — in either direction. Pass 1 corrected a per-*page* estimate that under-reserved
against whole-document requests; pass 2 then showed the whole-document request shape is itself the
defect, because it makes input quadratic and stops fitting the context window. Sending each page
exactly once restores the linear model pass 1 was right to reject only because the request shape
made it false.

So: **worst case per request = `(K × page_tokens + prompt_tokens) × input_price + max_tokens ×
output_price`**, and a document is `ceil(N / K)` requests. `prompt_tokens` — the instructions plus
the JSON schema, a measured module constant — is in the formula because a "worst case" that omits a
term is not a worst case, and `test_reservation_bounds_every_usage_table` asserts the bound. It is
~1% of a slice, but the only slack absorbing it would be the page constant, which is itself
unmeasured until I7b.

There is **no cache multiplier**, because there is no `cache_control` marker. The reason is not that
slices share no prefix — the system prompt and instructions *are* a shared prefix, rendered ahead of
the document block — but that the prefix is a few hundred tokens against `claude-opus-5`'s 512-token
cache minimum, so it very likely cannot be cached at all, and even cached it is ~1% of a request
dominated by 30,000 document tokens. Paying a 1.25× write premium to chase that is a loss.

The output bound is `max_tokens` — the request's hard output ceiling, which on `claude-opus-5` caps
thinking and response text *together*, so it is the correct and only safe bound. Reconciliation
folds the response's true `usage` (`input_tokens`, `output_tokens`) back in and returns the
difference to the running total.

**The whole document is checked against all three windows before the first call.** Per-call
reservation alone bounds each call and nothing else: with `per_operation_eur` and `daily_eur` raised
and the shipped `monthly_eur = 5.00`, a 200-page document reserving ~$14 proceeds to roughly call 15
and then refuses (out of the box `per_operation_eur = 0.05` refuses at call 1 and `daily_eur = 1.00`
at call 4, so this is the measurement KB's state, not a fresh install's), `on_exceed = "abort"`
stops the run, I7c's all-or-nothing rule writes no cache entry, and the user has spent the month's
budget with nothing in the index. The staging directory means the money is recoverable next month
rather than lost — but nothing told the user the run was doomed before it started, and
`--clear-cache` destroys the staging. So `reserve_document(estimate, caps, spent)` runs first and
refuses up front with the same three-window message, and `pnk sync` says how many documents in this
run it can afford. **It bounds the no-retry path, and says so**: I7b's ceiling is 6 semantic calls
per slice with the truncation retry at `max_tokens = 16000`, so a worst-case slice costs `5 ×
$0.3515 + $0.5515 = $2.31` — **6.6×** the single-attempt estimate, and $92 rather than $14 for 200
pages. Reserving at the worst case would refuse every real document under any shipped cap, so the
plan reserves at the estimate and states the multiplier in the same breath rather than letting a
reader infer a guarantee the number does not carry. The per-call checks are what actually stop the
spend; `test_an_unaffordable_document_is_refused_before_the_first_call` asserts the multiplier
alongside the refusal, so the gap is a tested constant rather than a surprise. The per-call checks
stay: they are what catches a run that drifts past its estimate mid-flight.

**`confirm_above_eur` prompts once per operation, against the whole-document estimate** — never per
call. DESIGN §5 places the prompt at estimate time, and a per-call reading with the shipped
`confirm_above_eur = 0.01` against a ~€0.32 slice would prompt **forty times** for one 200-page
document, which is how a confirmation becomes something a user learns to hold down `y` through.

**A context-window pre-check is part of the estimate, not an afterthought.** `K × page_tokens` plus
the prompt must fit the model's documented maximum input — 1M tokens on `claude-opus-5`. At K = 5
and the conservative 6,000-token page constant that is 30K, so it never fires in practice; it exists
because its absence is precisely what made the draft's design unimplementable at 166 pages while its
only size check tested a 600-page API limit that would never be reached. A check that cannot fire
under the shipped constants but names the exact limit that bounds them is cheap; discovering the
bound from a 400 at page 150 of a paid run is not.

**Worked example, the case the draft could not serve.** A 200-page scan at the conservative constant
is 40 requests: input `200 × 6,000 = 1.2M` tokens at $5/MTok = **$6.00**; output reserved `40 ×
8,000 = 320K` at $25/MTok = **$8.00**; plus `40 × 300` prompt tokens = **$0.06**, the term the
formula above calls non-optional — **$14.06 reserved**. Reconciliation returns about half the output
half (~$4.00, since five pages produce ~4,000 of the 8,000 reserved output tokens), so roughly 29%
of the reservation comes back. The same document under the draft's shape did not fit in the context
window at all, and at 100 pages reserved ~$375 of input plus ~$20 of output — a number no cap in
this plan can approve, so the feature would have failed closed with a refusal no user could satisfy.

**K = 5, and it is a semantic constant, not a tuning knob.** Output per request is then ~4,000
tokens against a `max_tokens` of 8,000 — 2× headroom, so truncation is rare and a truncation retry
re-asks five pages rather than twenty. Larger K needs a proportionally larger `max_tokens`, which
raises every reservation and makes each retry more expensive; K = 1 sends each page with no
neighbours, which loses a table or sentence continuing across a page break — the thing slicing at a
5-page boundary keeps in the common case. **K is hashed into the request-shape version** (I7b),
because the context a page is transcribed with is part of what produced its text: changing K is a
cache miss and a coherence refusal, not a silent re-tuning.

The per-page token constant is **measured**, not guessed, with `measured_on` recorded beside it.
Until that measurement (human-gated, I7b) it uses a documented conservative ceiling of **6,000 input
tokens per PDF page**, derived from the vendor's own documented high-resolution page budget (up to
~4,784 visual tokens for a rendered page, plus that page's text) — a per-page number applied to the
*actual* page count, never the API's 600-page maximum. The estimate ships its denominator as
`pages_estimated N of M`.

**Money is `Decimal` end to end, quantised once.** Every euro and dollar amount is `Decimal`;
`prices.toml`'s values parse as `Decimal`, not `float`. Quantisation to cents happens at exactly one
point — when a reservation or a reconciliation is **written to the ledger** — and comparisons
against caps are `<=` on the quantised value, so `spent + reserved == cap` proceeds and one cent
more does not. Stating this matters because the boundary tests assert exact equality: over floats
those tests are flaky, and a cap that is off by a representation error is not a hard cap. **It is
also work this increment must schedule**: `manifest.BudgetSection` types all three caps as `float`
today (`manifest.py:105-107`, parsed via `table.number`), so I6a converts them to `Decimal` and the
§2.1 `[budget]` amendment row covers the type change, not only the two new keys. A `Decimal`
reservation compared against a float-derived cap is the representation error wearing a different
hat.

`reserve.py` is the §5 accountant, and it is pure: `reserve(estimate, caps, spent) -> Decision`,
where `spent` is a `WindowTotals(operation, day, month)` the caller supplies. **Before every call it
checks all three ceilings** — `per_operation_eur`, the new `daily_eur`, and `monthly_eur` — and if
any of `spent.X + reserved` exceeds its cap the call is **never made**. The refusal names which
window blocked it and by how much. One operation being one `pnk sync` bounds a single invocation
only; the day and month windows are what stop a sequence of invocations, which is the failure mode a
hook-driven KB actually has.

`window.py` aggregates an in-memory list of ledger records by day/month in `[budget] timezone`;
reading the file is I6b's job, which is what keeps this half pure. `[budget]` gains
`max_price_age_days` (default 30) — an estimate against older prices is refused, not silently wrong
— and `daily_eur` (default 1.00, between the 0.05 per-operation cap and the 5.00 monthly one: a
burst limiter, where monthly is the real ceiling).

**How a reservation/reconciliation pair aggregates — the rule the draft never stated.** Every call
writes two ledger lines (I6b), and until this is pinned down the same ledger supports three
different totals: summing both lines double-counts every call and refuses at half the real cap;
counting only reconciliations makes an in-flight reservation invisible, so the cap is not a cap; and
counting reconciliations plus unreconciled reservations breaks at a window edge. The rule:

- **A pair is one record, attributed to the *reservation's* timestamp.** A call reserved at 23:59:58
  and reconciled at 00:00:03 belongs entirely to the first day. Attribution never moves.
- **The reconciliation supersedes the reservation's amount in place** — it does not add to it.
- **An unreconciled reservation counts at its reserved amount**, so an in-flight or crashed call
  consumes headroom rather than vanishing. It is reported as `unknown outcome`, never as zero.
- **A `void` record (I7b) closes a reservation at zero** — the escape hatch for a call that never
  billed, without which a handful of transient failures would permanently consume a month's budget.

Which reading applies is not academic, though the spread is narrower than it first looks and the
arithmetic is worth stating rather than gesturing at. At the shipped constants a slice reserves
`(30,000 + 300) × $5/MTok + 8,000 × $25/MTok = $0.3515` and reconciles at `$0.1515 + 4,000 ×
$25/MTok = $0.2515`. So counting reserved amounts buys **~70%** of what counting reconciled actuals
buys, and the widest spread across the three readings — double-counting versus reconciled-only — is
**~2.4×**. It cannot exceed 3.3× in principle, because the input half is fixed whatever the response
contains. A 2.4× error in a hard cap is still a hard cap that is wrong.

**The default caps refuse the paid extractor, and that is correct — but the refusal has to say so
completely.** One 5-page request at `max_tokens = 8000` reserves `30,000 × $5/MTok` input plus
`8,000 × $25/MTok` output = **$0.35**, which converts through `prices.toml`'s own `usd_per_eur` (a
bare euro figure here would be exactly the unprovenanced number I6b's ledger rule exists to
prevent). That is well past the €0.05 `per_operation_eur` default, which was sized for one `pnk ask
--deep` question. Raising it alone is **not sufficient** for any real document: `daily_eur` binds
next, then `monthly_eur`, and a refusal naming one cap at a time walks the user through three
sequential manifest edits to discover that. So the refusal prints **all three windows with their
current headroom**, the computed estimate, the complete manifest edit that would admit this run, and
one line stating the ongoing exposure that edit creates — because `--extract=claude-vision` is a
per-run override while a raised cap is permanent, and nothing in the draft acknowledged the
asymmetry. The plan does not lower `max_tokens` to sneak under a default that was never meant to
cover a 200-page document.

**Tests:** `tests/test_budget_core.py`, table-driven — the exact cap boundary for **each** of the
three windows (`spent + reserved == cap` proceeds; one cent more does not, asserted over `Decimal`),
and a case where the operation cap passes but the month's does not;
`test_reservation_bounds_every_usage_table` — hand-written `usage` records asserting the reservation
is never below the reconciled actual; `test_a_pair_straddling_midnight_is_attributed_to_the_start`
and its month-end and DST twins, in a non-UTC timezone — the aggregation that *produces*
`WindowTotals`, which the draft tested only downstream of a caller-supplied value;
`test_a_void_closes_a_reservation_at_zero`; `test_the_refusal_names_all_three_windows`;
`test_an_unaffordable_document_is_refused_before_the_first_call` (spy asserts zero calls, and the

### I6b — Budget I/O: the ledger, the prompt, `pnk budget`, and hooks that cannot spend

`budget/ledger.py` appends to `.pinakes/ledger.jsonl`; each line is a single sub-4KB `O_APPEND`
write, atomic on POSIX (§5). **The ledger stores no query text and no document content** —
timestamp, `operation_id`, `call_id`, record kind, operation kind, model, token counts, cost, KB id,
nothing more — and a test asserts it by running a paid extraction from a recorded fixture whose page
text contains a unique sentinel and grepping the whole ledger for it.

**Two identifiers, because the draft used one word for two things.** `operation_id` is one `pnk
sync` invocation — the unit `per_operation_eur` bounds. `call_id` is one API call — the unit a
reservation/reconciliation pair keys on, and what I4's cache entries join against. Collapsing them
made `per_operation_eur` ambiguous between "one sync" and "one call" in a section where the
difference is a factor of forty.

**Cost is recorded in USD with its conversion provenance, never as a bare number.** Each line
carries `cost_usd`, the `usd_per_eur` rate used, and the price table's `as_of`. EUR is computed at
read time. A ledger line that says only `cost: 0.043` is unreadable a month later — nobody can tell
which currency it is or which rate produced it — and the rate is exactly the number that drifts.
`pnk budget` shows, per window, which rate and which `as_of` its totals were computed with, and
flags a window that spans more than one rate.

**Three record kinds, keyed by `call_id`.** A **reservation** written *before* the call, then
exactly one of a **reconciliation** (the call returned; true `usage` supersedes the reserved amount
in place) or a **void** (the call never billed — cost zero, closing the reservation). That is the
durability answer (rule 12): a crash between the call and the ledger write would otherwise lose
spend history permanently, the one thing in `.pinakes/` that cannot be recomputed, and a reservation
with neither successor is reported as `unknown outcome`, not dropped and not counted as zero.

The `void` kind is what makes the protocol survivable. Without it, every call that *raises* — 429,
5xx, an oversize 400 — leaves a reservation nothing ever closes, and I6a's rule counts an
unreconciled reservation at its reserved amount. `ledger.jsonl` is append-only and CLAUDE.md forbids
editing it, so that phantom spend is permanent: a handful of transient failures would lock a user
out of their monthly budget with no way back short of a new month.

**A void is written only when no response was received, never from a bare `finally`.** A
`response_received` flag is set the instant `messages.create` returns, and only the not-received
path voids. A bare `finally` cannot tell "the call never happened" from "the call returned and then
schema branching or the staging write raised" — and in the second case it would record **€0 for
money that left the account**, permanently, in an append-only file. The plan guards the
phantom-charge direction thoroughly; this is the same defect pointing the other way, and it
under-counts rather than over-counts, which is the direction a budget system must never be wrong in.

**Timeouts are the residual, and they are bounded rather than left open.** A timeout may or may not
have billed, so it is neither reconciled nor voided; I6a counts it at its reserved amount forever,
which is the identical lockout the void exists to prevent — three timeouts consume the €1.00 day,
sixteen consume the €5.00 month. So `pnk budget` surfaces `unknown outcome` records prominently with
their total, `pnk doctor` WARNs once their total exceeds a quarter of any window, and **`pnk budget
--resolve <call_id> --actual <eur>`** appends a *reconciliation* for an operator who has checked the
vendor's usage dashboard. That is an append, not an edit: the ledger's invariant holds, and the
alternative is a KB that silently becomes unusable with no documented way back.

Reading the ledger into I6a's `WindowTotals`, under I6a's attribution rule, is this module's job;
the wiring is tested, not assumed.

`confirm_above_eur` prompts on a TTY. **When a confirmation is due and there is neither a TTY nor an
explicit `--yes`, the run aborts** — the scope matters: read broadly this would abort every
non-interactive sync, which is the shape of the pass-1 finding it was written to fix, so the abort
fires only when a confirmation is actually owed. `--yes` (required for cron) says in `--help` what
it authorises: it answers `confirm_above_eur`'s prompt, and **raises no cap**. It does **not**
answer `--clear-cache`'s confirmation when paid entries are present — `pnk sync --yes --clear-cache`
in a cron job would otherwise destroy paid extractions unattended, which is the behaviour the
verification row "`--clear-cache` cannot destroy paid results unattended" claims to forbid while
`--yes`'s stated scope permitted it. Clearing paid entries non-interactively requires the explicit
`--clear-cache=paid`, which no hook or CI workflow writes.

**Hooks and CI cannot spend.** DESIGN §6.3 makes `pnk sync` machine-driven — `pre-commit`,
`post-commit`, `post-merge`, and the workflow `pnk init --ci` writes — **except that `pnk init --ci`
does not exist**. DESIGN §6.3 designs it and v0.1 never shipped it (`init.py` takes `path`,
`--name`, `--template` only), so I6b **builds it here**, in the increment that needs it to force the
free backend: writing a modification to an unbuilt writer is the same defect as writing a hook
around an unbuilt flag. All four are non-interactive, so on a KB configured for `claude-vision` the
no-TTY abort above would kill hook-driven freshness on every single commit, and a `--yes` in a hook
would spend afresh on every commit with a fresh per-operation allowance each time. Resolution: `pnk
install-hooks` and `pnk init --ci` write `pnk sync --extract=pypdfium2` **explicitly** (the flag
exists from I1, so a hook written here is runnable here), forcing the free backend regardless of the
manifest, print one line saying so at write time, and carry the same line as a comment in the
generated hook. A machine-driven sync therefore indexes a scanned PDF's (empty) free extraction and
records it honestly — **and recoverably**, because I5's backend-drift rule makes that document stale
until a paid run picks it up, rather than skipped forever on a content hash that never changes
again. Paid extraction stays a deliberate human invocation. `pnk doctor` reports the combination
(paid backend configured, hooks installed and forcing the free one, N documents awaiting paid
extraction) so the split is visible rather than surprising. `make budget` wraps `pnk budget` and is
created **here**, by this increment — I9 only documents it.

`pnk budget` shows spend by day/month/operation with `reservations N, reconciled M, voided V,
unknown K` and the euro total held by unknowns; `pnk budget --resolve` is documented here. `pnk
doctor` gains a price-table check (OK, or WARN past `max_price_age_days` naming the file) and an
unknown-outcome check. **`monthly_eur` is per KB**, stated once here: the risk table's framing ("one
`pnk sync` is capped; nothing caps the tenth") holds one level up too, and a user with ten paid KBs
has ten monthly allowances. v0.2 does not add a global cap; it says so rather than leaving a reader
to assume one. **Tests:** `tests/test_ledger.py` — the sentinel test; a process killed between
reservation and reconciliation leaving a readable ledger and an `unknown outcome` row; a call that
raises leaving a `void` and **no** lasting headroom consumption; concurrent appends from two
processes interleaving no record; `--rebuild` and `--clear-cache` both leaving the ledger
byte-identical; every line carries `cost_usd`, `usd_per_eur` and `as_of`. `tests/test_cli_budget.py`
— `pnk budget` on an empty ledger printing zeros rather than a traceback; totals on a mixed ledger
matching a hand-computed fixture, including a window spanning two `usd_per_eur` rates; a
confirmation due with no TTY and no `--yes` exiting non-zero with a remedy, **and a non-interactive
run with nothing to confirm proceeding normally** — the two halves of L-6's ambiguity, one test
each; **a KB whose ledger already holds €4.99 of a €5.00 month refuses the next call even though the
operation cap is untouched** — the seam between I6a's arithmetic and I6b's ledger read, proved
rather than assumed. `tests/test_hooks.py` — `::test_hooks_force_the_free_backend` **executes** each
generated hook against a KB configured for `claude-vision` and asserts the sync ran with the free
backend and spent nothing (spy-counted). Asserting the string `--extract=pypdfium2` is *present* is
the string-assertion failure the ground rules exist to prevent: it passes on a hook that never runs.
A second, cheaper test keeps the grep as a readability check on all three hooks and the CI workflow.
**Exit criteria (repo-verifiable):** all of the above; §5 amended to say the machinery ships in v0.2
with all three windows enforced, and §8's v0.4 row updated in the same commit.

### I7a — The paid-path allowlist gate and the invariant amendments (lands first)

### I7b — The paid Claude-vision extractor: request shape, validation, retries

`src/pinakes/extract/claude.py` — **the only module in `src/` permitted to import `anthropic`**, and
the line I7a's allowlist gains in this commit. Registered as backend `claude-vision`, reached only
when the manifest says so or `pnk sync --extract=claude-vision` is passed. Every free step precedes
every paid one:

1. **Local pre-checks, zero cost** (PDFScout): page count, encryption detection, per-request size
  against the limit that can actually bind — **32 MB per request**, checked on the base64-encoded
  slice — **and against the model's context window** via I6a's pre-check. The documented 600-page
  and 100-page request limits are deliberately **not** checked: a request carries at most K = 5
  pages, so they sit 120× and 20× above anything a request can contain, and testing an unreachable
  limit is precisely the charge this plan levels at the draft it replaced. and the free extractor's
  own text yield against **I3b's fitted floor** — if the free path already clears it, the paid path
  **refuses to spend** unless `--force`, and says so. **The floor is per page and the decision is
  per document**, so the aggregation is stated rather than left to the reader: the paid path refuses
  when **fewer than 10% of pages** fall below the floor. A median would be the wrong statistic — a
  200-page report with eight scanned inserts has a healthy median and still needs the paid path —
  and 10% is what makes I8's worked example (8 of 200 = 4%, refused) come out the way I8 says it
  does. Paying to re-extract a healthy PDF is the most likely way a user loses money by accident.
  **With no fitted text-yield floor installed, this step refuses to spend at all** rather than
  proceeding without its guard (I3b). The 32 MB check is on the **base64-encoded** slice, not the
  raw bytes — base64 inflates by 4/3, so the effective raw ceiling is ~24 MB. A slice that exceeds
  it is **split in half and retried**, down to a single page; a single page that still exceeds it is
  a page failure naming the path and the size. Reducing K is not available, because K is hashed into
  the fingerprint.
2. **Estimate and reserve** through I6a, **before every single call**: the first attempt, every
  schema retry, the refusal retry and the truncation retry each take their own pre-call reservation
  and their own ledger pair keyed by `call_id`. §5 requires reserving before *each* call, and a
  single reservation covering a slice loop is not a cap. **Two ceilings, because there are two kinds
  of retry, and collapsing them into one constant is how the count went wrong twice.** A
  **semantic** budget of **6 calls** per slice — one first attempt, up to three schema retries, one
  refusal retry, one truncation retry (decision 12 removed the audit re-extraction that was the
  draft's seventh). And, *within* each of those, a **transport** budget of 2 backoff attempts for
  429/5xx. They are separate counters: one shared constant would let two early 429s silently consume
  the schema-retry budget and refuse a legitimate retry, an outcome no test could tell from a
  genuine exhaustion. Worst case is therefore **6 token-billed calls and up to 18 HTTP requests**
  per slice, and both numbers appear in the risk table rather than one standing in for the other.
  The client is constructed as **`Anthropic(max_retries=0)`**: the SDK's default of 2 silently turns
  one `messages.create` into up to three billed HTTP requests — and a request retried after a
  timeout can be billed twice for generation the server already completed — so the accountant, not
  the SDK, owns retry.
3. **Failure handling for calls that never return a response.** Step 5's branches cover HTTP 200s;
  this covers everything else, and without it the reservation written in step 2 is never closed. A
  **`void`** ledger record (I6b) releases the reservation at zero — written only when
  `response_received` is false, never from a bare `finally`, because a response that arrives and
  then raises during branching or staging *was* billed. Then: **429 and 5xx** retry with bounded
  exponential backoff, at most twice, each attempt taking a **fresh** reservation. **Timeouts** are
  billable-unknown: no automatic retry, the reservation stays `unknown outcome` rather than voided
  because the server may have generated, and I6b's `pnk budget --resolve` is the documented way out.
  **4xx other than 429** is a page failure with the API's message; it is deterministic, so retrying
  only spends again. **Connection-level errors** (`APIConnectionError`, a sibling of
  `APIStatusError` rather than a subclass) split by phase: a failure before any response byte is a
  void and retries; a failure mid-response is billable-unknown, like a timeout.
4. **Request shape — a K-page slice, not the whole document** (decision 8). `pdfium.slice_pages`
  writes a K = 5-page sub-document; it goes in a `document` content block placed **before** the text
  block — `{"type": "document", "source": {"type": "base64", "media_type": "application/pdf",
  "data": …}}`, newline-free base64, no beta header. **No `cache_control` marker**, for the reason
  I6a states: the shared prefix is real but almost certainly below the 512-token cache minimum and
  ~1% of a request in any case. Structured output via `output_config: {"format": {"type":
  "json_schema", "schema": …}, "effort": "low"}` — the current parameter, not the deprecated
  top-level `output_format`, and the reason citations are unavailable (they 400 together). The
  schema is an array of per-page objects and the response maps to pages **positionally**, so **an
  explicit `len(pages) == last - first + 1` assertion runs before that mapping**, treating a
  mismatch as a schema failure. The draft claimed the schema itself enforced this; array-length
  constraints are not something to rely on here, and the failure it prevents is the worst one in the
  increment — a 4-element response to a 5-page slice stores pages 2–5 under numbers 1–4, spans still
  tile, the cache entry is written, and the order-free completeness audit cannot see a page shift,
  so every citation for that document is silently off by one, for good. Thinking is **explicitly**
  `{"type": "disabled"}`: per-page transcription is not a reasoning task, thinking bills at the
  output rate, and `max_tokens` caps thinking and response together so an un-budgeted thinking phase
  would truncate the JSON body and burn paid retries. `claude-opus-5` accepts disabled thinking
  **only at effort `high` or below**, so the pair is pinned together as module constants. Of the two
  documented disabled-thinking failure modes, one is genuinely structural and one is not:
  tool-call-as-text cannot occur, because no tools are declared. But `output_config.format`
  constrains the response's **structure**, not its **string content** — a `<thinking>` fragment can
  land *inside* a page-text field and be cached, chunked and cited as extracted text. So three
  things, not one: the prompt carries the vendor's recommended **generic** instruction (*do not
  include internal or system XML tags in the response* — generic because naming thinking tags
  specifically is measurably less effective); the prompt carries **no** don't-think/don't-reason
  instruction, which increases leakage; and a page whose text matches a leaked-tag pattern is **a
  schema failure, retried, never silently stripped** — stripping would change the extracted text and
  would therefore have to enter the fingerprint. A tag-leaking recorded fixture proves the branch,
  because "checked rather than assumed" with no test behind it is assumed. The escape hatch, if the
  human-gated run shows otherwise, is adaptive thinking at `low` effort with `max_tokens` raised to
  budget for it — and the reservation follows automatically, because its output bound is
  `max_tokens`. `max_tokens` is **8000**, ~2× the ~4,000 tokens five pages of prose produce.
  `temperature`, `top_p` and `top_k` are never sent: they 400 on this model. `response.model` is
  recorded per slice in `per_page_provenance` — the documented idiom is
  `response.model.startswith(MODEL)`, and recording it is what would let a future fingerprint name
  the model that actually answered, which the "checked and declined" note on server-side fallbacks
  gives as the precondition for revisiting that feature.
5. **Per-slice validation with ≤3 schema retries** (PDFScout), branching in this order: `stop_reason
  == "refusal"` is checked **before reading `content`**, counts as a failure, is retried once and
  then recorded — the *cheap* failure, because a pre-output refusal is not billed at all.
  `stop_reason == "model_context_window_exceeded"` is a **hard** failure naming the slice and the
  computed token count: at K = 5 it should be unreachable, so reaching it means the page constant is
  wrong, and retrying an identical oversize request only spends again. `stop_reason == "max_tokens"`
  is checked **next, before schema validation**: a truncated response is invalid JSON, and without
  this branch it would be retried identically three times, all paid, all truncating at the same
  place. A truncated slice is re-asked **once** at `max_tokens = 16000` under a fresh reservation; a
  second truncation records a failure naming the pages. **A retry re-asks the whole slice, never a
  single page from it**: a page transcribed with different neighbours is a different extraction, and
  mixing the two inside one document is the provenance mess the fingerprint exists to prevent. The
  plan does **not** split a page: the sub-page boundary has no ground truth in the corpus, so a
  split would produce text nothing can score.
6. **Assembly runs the string policy and nothing else** (decision 10). The response is per-page text
  with no coordinates, so `blocks_from_chars`, `reading_order` and `strip_running_heads` have
  nothing to operate on; fabricating geometry to feed them would be invented data driving a stage
  that reasons about position. This backend builds `ExtractedText` from the per-page strings,
  applying `textpolicy.normalise()` — the one stage both backends share (decision 15).
  **`normalise()` is length-changing, so page offsets are computed *after* it**, exactly as I3a
  requires of the free path: ligature expansion turns one codepoint into two or three, and offsets
  taken before it would be out by one or two from the first ligature onward, while the spans still
  tile perfectly and no property assertion could see it. The pipeline difference that remains —
  running-head handling and reading order — is **measured in this increment's human-gated run**, not
  assumed away.
7. **The fingerprint.** `claude-vision`'s inputs, declared in I1's client-free registry entry, are
  `(backend name, model id, prompt version, schema version, request-shape version — which includes
  K, `TEXT_POLICY_VERSION`, pypdfium2 version, pdfium build)`. It includes the pdfium versions
  because this backend **does** load pypdfium2 — to slice, and to pre-check the free text yield. It
  includes `TEXT_POLICY_VERSION` because it runs `normalise()`, which changes the text. It
  **excludes `LAYOUT_VERSION`**, which it genuinely does not run (decision 15 is what makes that
  true rather than merely asserted). It **excludes `max_tokens`**, a budget knob rather than a
  semantic one — a slice re-asked at a higher cap yields *more complete* text of the same kind, and
  hashing it would change the fingerprint mid-run at exactly step 5's retry. Changing `[extraction]
  model` or K produces a cache **miss** and, on an already-built index, the §4.4 **WARN and
  stale-extraction marker** decision 13 defines — not a refusal, because the remedy would be an
  invoice.
8. **`--estimate-only`.** Builds the real request for the first slice and calls
  `client.messages.count_tokens` to measure exact input tokens without generating anything, then
  prints the extrapolated whole-document estimate and exits. It tightens the reservation constant at
  a fraction of a real run's cost, and it is the documented first step of the human-gated
  measurement below. **It is a network call, not an offline estimate** — stated in `--help`, in §6.3
  and here, because "estimate" reads as free and this one requires a key. It is never *required*:
  the estimate must exist on an install with no client at all.

### I7c — The completeness audit, staging, and all-or-nothing commit

1. **Completeness audit — report-only in v0.2** (decision 12). `word_coverage` is computed per page
  against pypdfium2's native layer and **reported**; nothing is re-extracted and nothing is spent.
  Pages with no usable native layer (the scanned stratum) are **exempt and reported as exempt**,
  with their denominator: `audited N of M, exempt K of M, below-median P`. The re-extraction loop
  needs a floor, and I3b explains why no honest floor exists before paid output does — the applied
  pair is (native layer → Claude) and no Claude output exists at fitting time. So v0.2 ships the
  measurement and **v0.3 ships the loop**, fitted on the distribution this release's first real runs
  produce. This is the release's own rule applied to itself: a threshold that spends money is fitted
  or it does not exist. It also removes an inconsistency the loop had inherited — the audit
  re-extracted a *page* while I7b forbids re-asking a single page from a slice, and the estimator
  has only a per-slice formula. Nothing that does not run needs that contradiction resolved. `pnk
  doctor` and the sync report surface the low-coverage pages by path so a human can decide.
2. **Staging and commit.** Each validated page is written to
  `cache/extract/partial/<hash>-<fingerprint>/<page>.json` (temp + `os.replace`) as it completes, so
  an interrupted 200-page run does not re-pay for pages already extracted. Under decision 8 the
  resume is **genuinely free of re-payment for staged pages**: each request carries only its own
  slice, so there is no prompt cache to re-prime and no 1.25× write to re-pay — the draft's honest
  caveat about a 5-minute TTL simply no longer applies. Resume granularity is the **slice**: a slice
  interrupted mid-flight is re-asked whole, because its pages were transcribed together. Only when
  every page passes is the single complete cache entry written and the staging directory removed. A
  partially extracted document writes **no** complete entry and goes to `failures`; `on_exceed =
  "partial"` is honoured at the corpus level (completed documents keep their entries, the run stops
  cleanly), never at the page level — a half-extracted document in the index is the silent
  truncation §4.6 exists to prevent. **DESIGN §5 gains that definition in this commit**: it is a
  rule about what `partial` means, and §5's existing amendment row covers only the opening sentence
  and the control table.
3. **`--clear-cache` learns what it is destroying.** Its printed summary (I4) gains the euros the
  cached entries cost, joined from the ledger on the entry's `call_ids` (I4) — the draft said "by
  operation id", which no cache entry recorded and no ledger line could be matched to, so the
  behaviour its verification row asserts was unimplementable as specified. CLAUDE.md's

  except the paid extraction cache too: those entries are derived state that costs real money to
  derive, which is a different thing from disposable. I4's automatic eviction already spares them,

4. **Flag scope, stated once and in `--help`.** The complete list, so none of them can arrive
  without a stated scope again: `--extract=BACKEND` (I1) overrides `[extraction] backend` for one
  run. `--estimate-only` (I7b) measures and exits, **and makes a network call**. `--yes` (I4)
  answers `confirm_above_eur`'s prompt and raises no cap; it does **not** authorise destroying paid
  cache entries. `--clear-cache` (I4) empties the free extraction cache after confirming;
  `--clear-cache=paid` is the explicit form required to destroy paid entries, and no hook or CI
  workflow writes it. `--force` bypasses **exactly two things**, both refusals to spend or discard

### I8 — `pnk doctor` text yield, `path:page` citations on both surfaces, and the trace passes

`pnk doctor` gains a `text yield` check over PDF documents. **It reports and thresholds per page,
not per document.** A document-level median against a per-page floor is a different statistic from
the one I7b spends against, and it hides the case that matters: a 200-page report with eight scanned
inserts has a healthy median, so the check stays silent *and* I7b's pre-check refuses to pay for it.
So: `median C chars/page over N of M PDF documents`, plus `pages below floor: P of Q`, listing by
path **and page**. The floor is I3b's, fitted there on the I2 corpus and shipped in `floors.toml`,
so the increment that spends against it (I7b) and the increment that reports it (I8) consume one
number neither invented; with the floor absent the check reports the distribution and says the floor
is missing rather than inventing one. Its remedy names the paid path and its cost rather than "out
of scope".

**Page citations ship on both surfaces, in the same increment.** DESIGN §1's first decision is
"agent-first", and v0.1 pass 2 established one filter vocabulary across two surfaces; shipping page
provenance on the CLI and not on MCP would recreate exactly the divergence v0.1 fixed, in the
release whose entire goal is page-citable PDFs, on the surface the design calls primary. So:

- `pnk search` renders `path:page` in citations — **and `path:p1-p2` when a chunk spans two or more
  pages**, which I5 explicitly allows and the draft's singular rendering had no answer for; `--json`
  carries `page_start`/`page_end` as separate fields either way. **The shape is already taken**:
  `search.py:64-66` renders `f"{path}:{char_start}-{char_end}"` today, so `report.pdf:12-480`
  currently means *character offsets* and `report.pdf:12-13` would mean pages — same syntax, two
  meanings, silently. PDFs therefore render `path:p12-13` with an explicit `p`, and non-paged
  sources keep today's bare offsets unchanged. A citation format that can be misread is worse than
  one that is ugly.
- `pinakes_search` results carry `page_start`/`page_end` (null for non-paged sources).
- `pinakes_get` accepts an optional page range and marks page boundaries in what it returns, so an
  agent can cite `path:page` from a `get` as well as from a `search`.

**Trace one datum end to end** (rule 2 — the two most expensive plannable misses in v0.1 were both
producer/consumer *name* agreement with *column* disagreement, and five consistency passes could not
see them). Three tests in `tests/test_pdf_trace.py`:

1. `test_a_table_cell_word_survives_every_hop` — one word from a value cell of the bordered-table
  fixture, six hops, each asserting against the value carried from the previous one: **extraction**
  (the word is in `ExtractedText.text` at offset `o`, page `p`) → **cache** (the cached JSON for
  that content hash yields the same `o` and `p`) → **chunk** (**at least one** chunk has `char_start
  <= o < char_end`, and **every** such chunk contains the word and reports `page_start == p`) →
  **FTS** (`SELECT rowid FROM chunks_fts WHERE chunks_fts MATCH …` returns that chunk's rowid) →
  **CLI** (`pnk search` returns that passage with `path:p` in the rendered citation) → **MCP**
  (`pinakes_search` returns the same passage with `page_start == p`). The last two hops assert the
  *same* page number, which is the only way a CLI/MCP divergence is visible. **"Exactly one" was
  wrong and would have made this test pass or fail by fixture accident.** Verified in
  `chunk.py:239-269`: `_fit` prepends the carried overlap tail and sets `start` from the *carried*
  piece's position, so chunk *n+1*'s `char_start` lies strictly inside chunk *n*'s range whenever a
  block splits — and I5's own text says "≥1 chunk". A table cell is the fixture most likely to be
  one oversize block that `_atomise` splits, so the contradiction sits exactly where the test aims.
  Asserting the property over *every* matching chunk is strictly stronger than asserting there is
  one.
2. `test_every_filter_dimension_resolves_for_pdfs` — every dimension a PDF can be selected by
  (`source_type`, `path_prefix`, `mtime`, `tags`) **returns the expected PDF rows when actually
  filtered on**. The draft asserted each resolves to a column "non-null for every PDF row", which is
  wrong for `tags` and vacuous besides: verified in `store.py:38-48` and `search.py:128-132`, tags
  are not a column at all but `json_each(d.metadata, '$.tags')` over a `metadata` field that is `NOT
  NULL DEFAULT '{}'` — so the non-null assertion is true by schema for every row, PDF or not, and
  would pass on a corpus where no PDF has a single tag. Exercising the filter is the only version of
  this test that can fail.
3. `test_a_paid_slice_traces_from_estimate_to_the_budget_report` — the money equivalent, and the
  reason the risk table aims at machinery: one **slice's** cost from **estimate** → **reservation
  line** → the recorded response's **`usage`** → **reconciliation line** → the total `pnk budget`
  prints. The unit is the slice, because after decision 8 no per-page number exists anywhere in the
  money machinery and a trace whose unit nothing produces cannot assert against the layer below it.
  Each hop asserts against the previous one's number, so a unit slip (tokens vs MTok, USD vs EUR)
  cannot hide in an intermediate layer.

**Tests (beyond the traces):** `tests/test_serve.py::test_mcp_search_carries_page_spans` and
`::test_mcp_get_is_page_aware`; `tests/test_doctor.py::test_text_yield`. **Exit criteria
(repo-verifiable):** all three trace tests pass; both MCP tests pass; the doctor check WARNs on the
scanned fixtures and is OK on the baseline; `--help`, the MCP tool descriptions and README show the

## Durability sweep (rule 12)

*Which writes lose unrecoverable information if interrupted?*

- **`ledger.jsonl` — the only genuinely unrecoverable write, and it is new.** A crash between the
  API returning and the ledger append loses spend history permanently: money left the account and
  nothing records it. Answered by I6b's reservation → reconciliation-or-void protocol — a torn write
  degrades to a *visible* `unknown outcome`, never to a silent zero, and a call that never billed is
  closed at zero rather than consuming a month's headroom for good.
- **Paid staging entries — recoverable, but only at cost.** Regenerable in principle, and that
  regeneration is exactly what the user is paying for; written per page, atomically, consumed on
  resume (I7c). Without them an interrupted 200-page run re-pays for everything. **With them and
  decision 8's slicing, a resume re-pays for nothing already staged** — each request carries only
  its own slice, so there is no vendor-side cache to re-prime; the only re-payment is the slice that
  was in flight.
- **Free cache entries — recoverable and free. Paid cache entries are not.** Both are atomic: a
  half-written JSON that happens to parse is worse than a miss. **The eviction sweep** is the only
  new delete — derived state only, only after a fully successful sync, guarded and tested (I4) — and
  it **skips paid entries entirely**, because "derived" and "free to re-derive" are different
  properties and only the second one licenses a silent delete.
- **Sidecars for PDFs — unchanged and already atomic** (v0.1 I5, rename-based). Re-asserted rather
  than assumed: the ULID a sidecar carries is still the one thing no later command can recompute.
- **The `-wal`/`-shm` lesson (v0.1 I8b) transfers:** cache and staging are *sets* of files under
  directories, so `--clear-cache` and the sweep are tested by listing the directory afterwards,
  never by trusting that one `unlink` was enough.

## Risks specific to this sequencing

Aimed at **machinery**, deliberately: v0.1's risk table enumerated algorithmic risk, and all seven
of its HIGH findings came from areas it never contemplated — durability, file naming, boundary
arithmetic, vacuous metrics, and the gate itself.
